# 回放问题重开责任台账启用说明

本功能入口位于“回放问题清单 → 重开责任调整”。当前页面直接展示人员与批次统计，人员表仅有负责人和问题数。问题数按每次重开计 1，可按全部、查询（RPT）、动账（DZ）筛选并多选发生批次。列表中的“累计重开”跟随 `issue_key`。正式设计位于 Obsidian 的 `01 Engineering/axon-link-server/回放问题重开责任调整-系统设计.md` 及配套数据模型、API 接口页。

## 1. 数据库与配置

在结果库（`diiResultJdbcTemplate` 对应的 MySQL）人工执行 `src/main/resources/db/daoindex/V85__replay_issue_reopen_attribution.sql`，确认六张新表创建成功并使用支持事务和行锁的 InnoDB。该工程没有自动执行本迁移的启动流程。

2026-11-09 增加授权数量转移。使用该功能前再执行 `src/main/resources/db/daoindex/V90__replay_reopen_count_transfer.sql`，创建保存请求幂等信息与已转事件范围的请求表。迁移可重复执行。已有事件表、审计表与该请求表均须使用 InnoDB。

配置由部署环境提供，示例如下。两组名单均按当前有效用户的身份匹配：有工号时填写 `emp_no`，只有工号为空时才填写 `username`；名单和身份首尾空白会去除，大小写必须一致。

```yaml
dii:
  replay:
    issue-reopen:
      enabled: true
      admin-emp-nos:
        - "实际管理员工号或无工号管理员账号"
      count-transfer-emp-nos:
        - "实际次数调整人员工号或无工号人员账号"
```

默认 `enabled=false`、管理员列表为空。管理员仅管理领域审批授权、待审转派和历史回填；如需审批，仍必须在对应领域被显式授权。功能启用后，正常导入中的计次与原导入使用同一事务，记账失败会回滚该次导入。

`count-transfer-emp-nos` 默认空列表，管理员与次数调整两个名单独立授予权限。2026-11-23 起兼容 `emp_no` 为 NULL、空串或全空白的有效账号，按用户名匹配；已有非空工号的账号继续只匹配工号。LDAP 首登自动同步且无工号的人员，维护用户名到对应名单即可，不需要补写虚构工号。配置变更后重启实际服务实例并重新打开台账。

配置中的人员点击问题数，选择目标开发负责人，填写调整数量和原因后直接提交。后端在每次写入时重新校验有效账号及当前名单，并将所选范围内的来源人员次数原子转给目标人员，记录操作者、原因、原负责人、目标负责人和时间。本人可承担转入次数。待审申请占用的次数暂不参与调整，页面展示可调整数量。

部署前端时在前端仓库使用明确输出目录，例如 `npx vite build --outDir /tmp/axon-reopen-release`，检查产物后沿用现有发布流程。不要为验证运行默认构建：现有 Vite 配置会清空后端 `src/main/resources/static`。

## 2. 既有审批接口的领域授权

历史申诉与审批由既有后端接口处理。管理员通过 `PUT /api/ai/parallel-replay/issues/reopens/policies/{domain}` 为问题所属领域选择有效领导账号和主审批领导，填写授权调整原因后保存。当前统计页面的数量转移使用独立权限配置。领域可配置备选领导用于本人责任回避，缺少有效领导时申请会提示补充授权。

可以撤销全部领导授权。撤权立即阻止新的裁定，已有待审申请仍保留，管理员可填写原因后显式转派给新的授权领导。管理员没有隐式代审批权限。

只有交易人员映射中的有效开发账号可被选作责任人。发生重开时若仅有一名有效开发负责人，系统默认归责给该账号；映射多人、缺失或账号无效时记录“待归属”，由该领域领导选择负责人并填写确认原因。后续人员映射变化不追溯改写历史默认责任。

## 3. 历史回填

先完成人工迁移和授权，再使用管理员身份调用：

```http
POST /api/ai/parallel-replay/issues/reopens/backfill
Content-Type: application/json

{"afterRoundEntryId":0,"limit":500}
```

响应 `data` 包含 `scanned`、`inserted`、`nextRoundEntryId`、`hasMore`。将 `nextRoundEntryId` 作为下一次游标，直到 `hasMore=false`；重复执行同页不会重复计次。回填只采纳历史轮次中明确的“修复待验证 → 重新打开”转换。无法从历史恢复开发归属的次数保留为待归属，不使用今天的映射推断旧责任。历史批次数据不完整时，累计值代表可核实的记录，不能补造事实。

全量刷新用于修正当前基线，不生成新重开次数，也不删除已有永久台账。

## 4. 验收流程

1. 正常导入触发实际状态转换后，确认 `issue_key` 累计加一；重复导入不增加，再修复后真实重开会再次增加。
2. 在人员与批次统计选择交易类型及一个或多个发生批次，应用筛选后核对人员问题数之和与所选范围重开总次数。
3. 使用已配置 `count-transfer-emp-nos` 的账号点击某人的问题数，选择其他有效开发负责人，填写数量和原因。提交后来源人员减 N、目标人员加 N，所选批次及全部批次总次数守恒。
4. 普通账号看到只读数字，直接调用 `POST /api/ai/parallel-replay/issues/reopens/count-transfers` 同样受到后端权限校验。待归属以及历史停用人员的次数可以由授权账号转出。
5. 对同一 `requestId` 原样重试应返回第一次的操作结果，数量和审计只执行一次。同一请求标识修改载荷返回冲突。
6. 数量超出可调整范围、选中类型与批次不匹配、记录被并发调整时整笔失败。核对请求记录和事件审计中的操作者、原因、时间和前后责任人。历史申诉、审批及复核接口可按其独立契约继续验收。

## 5. 回退

先将 `enabled` 设为 `false` 并重启应用，可恢复原导入路径并让前端显示未启用状态。保留六张永久台账表及已有事实；恢复时重新启用即可。关闭期间产生的可核实历史转换可之后回填。回退代码或恢复数据库按现有发布流程执行。

## 真实 API 模式

运行入口使用正式前端 `/src/main.js`，所有业务请求使用同源 `/api`。清单、选项、轮次、人员、计次、申请、审批、归属、权限与统计均调用现有 Java 控制器；不安装浏览器 fetch Mock 拦截，不用演示身份或失败时的模拟记录回填。测试 fixture 仅保留在测试范围。

开发服务的真实后端地址统一由 `AXON_REAL_API_TARGET` 配置（进程环境或前端 `.env.local`），默认 `http://localhost:8123`。部署时同源请求继续由实际后端处理。18769 预览也复用该配置，支持 `/#replay-issues` 直达清单。后端未连接时页面显示错误；账号查询失败显示“未获取账号”，不会默认展示管理员身份。

本次独立核对：清单 API 42 个函数及重开 API 17 个封装均有后端对应路由。真实网络数据连通仍取决于运行中的后端、数据源和已执行的迁移；当前默认8123未监听，不以本地 H2 代替真实数据。
